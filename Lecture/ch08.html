8.1 모델 크기 선택

요리 양에 맞는 냄비 고르기

🍲 비유

모델(파라미터 수), 데이터(토큰 수), 계산 자원(GPU 시간)은 서로 균형이 맞아야 합니다. 냄비(모델)가 너무 작으면 재료(데이터)를 다 못 담고, 냄비만 너무 크면 재료와 시간(계산량)이 부족해 낭비입니다. WebBot은 CodeBot·StoryBot보다 레이어 수, 임베딩 차원, 컨텍스트 길이를 모두 키워 더 많은 데이터를 담을 수 있게 설계합니다.

8.2 FlashAttention

큰 표를 통째로 인쇄하지 않고 필요한 부분만 계산

🧾 비유 — 효율적인 회계

일반적인 어텐션은 컨텍스트 길이 × 컨텍스트 길이 크기의 거대한 점수 표(scores)를 만들어 느린 메모리에 저장한 뒤 처리합니다. FlashAttention은 이 표를 통째로 만들지 않고, 작은 블록 단위로 계산과 합산을 동시에 진행해 빠른 메모리(GPU 캐시)만 사용합니다 — 전체 장부를 인쇄해 훑어보는 대신, 그때그때 필요한 몇 줄만 암산으로 처리하고 결과만 기록하는 회계사와 같습니다. 결과는 수학적으로 완전히 동일하지만 훨씬 빠르고 메모리를 적게 씁니다.

# webbot/model.py — PyTorch의 SDPA가 내부적으로 FlashAttention 커널을 사용
hidden = F.scaled_dot_product_attention(Q, K, V, is_causal=True, enable_gqa=True)
8.3 Grouped-Query Attention (GQA)

질문자는 많아도, 참고 자료실은 소수만 공유

🗂️ 비유 — 공용 자료실

2장의 멀티헤드 어텐션은 헤드마다 각자의 Query·Key·Value를 따로 가집니다. 헤드 수가 많아질수록 KV 캐시(5장)도 그만큼 커져 메모리를 많이 씁니다. GQA는 Query 헤드는 그대로 여러 개 두되, Key·Value는 몇 개의 그룹이 공유하게 합니다 — 회사에 질문하는 직원(Query)은 많아도, 실제 자료(Key·Value)를 보관하는 공용 자료실은 소수만 두고 여러 직원이 함께 참고하는 것과 같아 캐시 메모리를 크게 절약합니다.

# webbot/model.py — n_head=12 (질문자 12명), n_kv_head=4 (자료실 4개, 3명씩 공유)
self.W_q = nn.Linear(E, n_head * D)      # Query: 12개 헤드
self.W_k = nn.Linear(E, n_kv_head * D)   # Key:   4개 그룹만
self.W_v = nn.Linear(E, n_kv_head * D)   # Value: 4개 그룹만
8.4 전문가 혼합 (MoE)

환자마다 필요한 전문의 한두 명에게만 진료 배정

🏥 비유 — 종합병원

하나의 거대한 FFN 대신, 여러 개의 "전문가(expert)" FFN을 두고 각 토큰마다 라우터(접수처)가 가장 적합한 전문가 1~2명에게만 처리를 맡깁니다. 병원에 전문의가 수십 명 있어도(전체 파라미터는 많음), 환자 한 명이 실제로 만나는 의사는 한두 명뿐인 것(실제 연산량은 적음)과 같습니다. 그 결과 모델의 "지식 용량"은 크게 늘리면서도, 매 토큰을 처리하는 실제 계산량은 크게 늘지 않습니다.

이 저장소의 WebBot은 MoE를 사용하지 않는 단일 FFN(SwiGLU) 구조지만, GPT-4·Mixtral 등 최신 대형 모델들이 널리 채택하는 방식입니다.

8.5 torch.compile

즉석 통역 대신 미리 최적화된 리허설

🎬 비유

파이토치는 기본적으로 한 줄씩 즉석에서 실행합니다(eager mode) — 매번 새로 통역하며 말하는 것과 같습니다. torch.compile은 모델의 연산 전체를 미리 분석해서 더 빠른 형태로 "컴파일"해둔 뒤 그대로 반복 실행합니다 — 대본을 미리 리허설해서 최적의 동선을 짜두고 그대로 공연하는 것과 같아, 반복되는 학습 루프에서 상당한 속도 향상을 얻습니다.

# ch09/01_pretrain.py
model = GPT(vocab_size, context_len, embed_dim, n_head, n_kv_head, n_layer, ff_dim, theta)
model = torch.compile(model)   # 딱 한 줄로 적용
8.6 컨텍스트 길이 확장

연습해본 적 없는 넓은 범위의 시험 대응하기

📏 비유

모델은 학습 때 정해진 컨텍스트 길이(예: 1,024토큰)까지만 위치 패턴을 경험합니다. 더 긴 문맥을 다뤄야 할 때는, RoPE(5장)의 회전 각도 스케일을 조정해 "이전에 배운 회전 패턴"을 더 넓은 범위로 늘려 재활용하는 기법(RoPE scaling)을 사용합니다 — 중간고사 범위로 공부했지만, 그 풀이 패턴을 응용해 기말고사의 넓은 범위에도 대응하는 것과 비슷합니다.

8.7 정리

8장 핵심 요약

  • 모델 크기는 데이터·계산 자원과 균형을 맞춰 선택
  • FlashAttention: 결과는 동일하지만 메모리 접근을 최소화해 훨씬 빠른 어텐션 계산
  • GQA: Query는 여러 개, Key·Value는 소수 그룹이 공유 → KV 캐시 메모리 절약
  • MoE: 여러 전문가 중 일부만 활성화 → 지식 용량 ↑, 연산량은 절제
  • torch.compile로 실행 속도 향상, RoPE 스케일링으로 컨텍스트 길이 확장

QUIZ 1

GQA에서 여러 Query 헤드가 공유하는 것은?

정답: Key와 Value. Query 헤드 수는 그대로 두되, 소수의 Key·Value 그룹을 여러 Query 헤드가 함께 참조해 KV 캐시 메모리를 절약합니다.
QUIZ 2

MoE(전문가 혼합)의 핵심 아이디어는?

정답: 두 번째. 전체 파라미터(지식 용량)는 늘리되, 토큰 하나당 실제로 활성화되는 전문가 수는 적게 유지해 연산량을 절제합니다.
