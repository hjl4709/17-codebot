WebBot은 CodeBot(어휘 1,000개)·StoryBot(어휘 10,000개)보다 훨씬 큰 어휘 50,000개를, 훨씬 큰 인터넷 텍스트(OpenWebText)로 학습합니다. 4장의 최적화만으로는 부족한 지점과, 토크나이저 설계의 더 넓은 선택지를 살펴봅니다.

7.1 WebBot의 토크나이저

같은 코드, 훨씬 큰 무대에서

WebBot은 4장에서 만든 StoryBot의 최적화된 BPE 구현을 그대로 재사용하되, 어휘 크기와 데이터 규모만 훨씬 키웁니다.

from storybot.tokenizer import train_bpe

vocab_size = 50000                       # StoryBot(10,000)의 5배
file_path = "webbot/owt_train.txt"          # OpenWebText: 인터넷 글 모음
merge_rules = train_bpe(file_path, vocab_size, num_processes=8, num_chunks=64)
📚 비유

같은 조리법(BPE 알고리즘)이라도, 4인분 요리와 400인분 케이터링은 준비 방식 자체가 달라집니다. 어휘와 데이터가 커질수록 4장의 최적화(분할·병렬·캐시)가 선택이 아니라 필수가 됩니다.

7.2 병목 지점 찾기

어디서 시간이 새는지 스톱워치로 재보기

⏱️ 비유 — 요리 시간 측정

요리가 늦어질 때 "재료 손질이 오래 걸리나? 불 조절이 문제인가?"를 단계별로 재봐야 원인을 알 수 있습니다. 소프트웨어에서는 이를 프로파일링(profiling)이라 부릅니다. 코드의 각 부분이 전체 실행 시간 중 얼마를 차지하는지 측정해서, 무작정 최적화하는 대신 가장 느린 부분부터 손을 댑니다.

이 저장소에는 프로파일링 실습 코드가 따로 없지만, 실제로는 파이썬 표준 라이브러리의 cProfile이나 line_profiler 같은 도구로 병목을 찾습니다 — 대개 문자열 처리와 병합 반복문이 가장 무겁습니다.

7.3 러스트와 C++를 이용한 속도 개선

무거운 일은 근육질 전문가에게 아웃소싱

💪 비유

파이썬은 다재다능하지만 반복문이 느립니다. 병목이 된 핵심 반복 구간(병합 루프 등)만 러스트나 C++처럼 훨씬 빠른 언어로 새로 작성하고, 파이썬에서는 그 결과만 불러 쓰는 방식입니다 — 매니저(파이썬)는 전체를 총괄하고, 힘쓰는 작업(반복 계산)은 근육질 전문 일꾼(러스트/C++)에게 맡기는 것과 같습니다. 실제 프로덕션 토크나이저(예: OpenAI의 tiktoken)도 이런 방식으로 러스트로 핵심부를 구현합니다.

이 저장소는 순수 파이썬 구현에 집중하지만, 같은 알고리즘을 저수준 언어로 옮기면 보통 수십 배 이상 빨라집니다.

7.4 특수 토큰 추가

대화의 신호등과 표지판

🚦 비유

1장에서는 <|endoftext|> 하나만 있었지만, 실전 챗봇은 "여기부터 사용자 발화", "여기부터 시스템 지시", "여기부터 모델 응답"처럼 더 많은 역할 표시가 필요합니다. 특수 토큰은 도로의 신호등·표지판처럼, 모델이 "지금 누가 말하고 있고 어디서 멈춰야 하는지"를 명확히 알게 해주는 약속된 기호입니다.

<|user|> 파이썬으로 정렬 함수 짜줘 <|end|>
<|assistant|> def sort_list(lst): ... <|end|>
7.5 다른 토크나이저

BPE만이 정답은 아니다

방식핵심 아이디어비유
BPE (이 책)자주 붙는 쌍을 반복 병합자주 쓰는 줄임말 만들기
WordPiece병합 시 우도(likelihood) 최대화 기준 사용"가장 그럴듯한" 조합 우선 선택
Unigram (SentencePiece)큰 어휘에서 불필요한 토큰을 제거해가며 축소과한 재료를 덜어내며 레시피 완성
tiktoken (OpenAI)BPE + 러스트 고속 구현같은 조리법, 전문 주방 설비

목적(속도, 언어 다양성, 어휘 크기)에 따라 적합한 방식이 달라집니다.

7.6 토크나이저를 사용하지 않는 접근법

통역사 없이 원어민처럼 바로 대화하기

🗣️ 비유

토크나이저는 편리하지만 "번역 손실"이 생길 수 있습니다(예: 오타나 신조어를 이상하게 쪼갬). 바이트/문자 단위로 직접 처리하는 모델은 통역사 없이 원어(바이트)로 바로 대화하는 것과 같아서 손실은 없지만, 문장이 훨씬 길어져 더 많은 계산이 필요합니다. 최근에는 이 둘의 장점을 섞은 바이트-레벨 하이브리드 접근도 연구되고 있습니다.

7.7 정리

7장 핵심 요약

  • WebBot은 4장의 최적화된 BPE를 어휘 50,000개 · 인터넷 규모 데이터로 확장 적용
  • 프로파일링으로 병목을 찾고, 정말 느린 곳만 러스트/C++로 아웃소싱
  • 특수 토큰을 늘려 대화의 역할과 경계를 더 세밀하게 표시
  • BPE 외에도 WordPiece, Unigram 등 다양한 서브워드 방식이 존재
  • 토크나이저 없는 접근(바이트/문자 단위)은 손실은 없지만 시퀀스가 길어지는 트레이드오프
